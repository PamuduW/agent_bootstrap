# OpenClaw Adapter Plan

This document is the working blueprint for adding an OpenClaw surface to
`agent_bootstrap` without breaking the current Bootstrap-first model.

Last reviewed: 2026-04-11

## Goal

Keep this repo as the canonical control plane and add OpenClaw as another
adapter, not as a second source of truth.

That means:

- authored instruction files stay as `global/AGENTS.md` and `<repo>/AGENTS.md`
- OpenClaw-specific files are generated outputs
- external skills are reviewed, normalized, and curated before they become
  managed packages
- no direct "mirror everything from ClawHub" workflow

## Current OpenClaw Runtime Facts

Based on the current OpenClaw docs and ecosystem references:

- OpenClaw uses a workspace directory as the agent runtime `cwd`
- the workspace expects user-editable bootstrap files, including
  `AGENTS.md`, `SOUL.md`, `TOOLS.md`, and a one-time `BOOTSTRAP.md`
- OpenClaw also supports additional workspace memory files such as
  `HEARTBEAT.md`, `IDENTITY.md`, and `USER.md`
- OpenClaw skills can be installed globally or per-workspace, with workspace
  skills taking precedence
- onboarding supports non-interactive setup and provider auth choices
- OpenAI/Codex-style auth is a better fit for this machine than an API-key-only
  path when available

## Canonical Model Mapping

The canonical authored model in this repo stays unchanged:

- global baseline: `global/AGENTS.md`
- repo overlay: `<repo>/AGENTS.md`

The OpenClaw adapter should render these files:

- `AGENTS.md`
  Source: merged global + repo canonical instructions
- `SOUL.md`
  Source: adapter-owned template plus optional repo-local overrides later
- `TOOLS.md`
  Source: generated surface/tool notes based on enabled packages, MCP ownership,
  and local conventions
- `BOOTSTRAP.md`
  Source: generated one-time setup note for first run only

The adapter should not treat any of those generated files as authored truth.

## Recommended Ownership Rules

- `AGENTS.md` remains canonical in this repo and in target repos
- generated OpenClaw files are disposable and can be re-rendered at any time
- `USER.md` and `IDENTITY.md` should remain user-owned unless we explicitly add
  support for managing them
- `HEARTBEAT.md` should be opt-in only, not generated by default

## Workspace Strategy

Use OpenClaw workspaces as render targets, not as the source system.

Recommended render targets:

- global OpenClaw workspace:
  `~/.openclaw/workspace/`
- repo-specific OpenClaw workspace:
  `<repo>/.openclaw-workspace/` or another explicitly managed adapter path

Why this split helps:

- it keeps OpenClaw state isolated from the canonical repo files
- it avoids teaching users to hand-edit generated outputs
- it makes re-render and reset operations safer

## Skill Path Strategy

OpenClaw currently supports multiple skill locations with precedence. Use that
to separate curated generated content from user-owned overrides.

Recommended policy:

- `~/.openclaw/skills/`
  Bootstrap-managed global generated skills
- `~/.agents/skills/`
  user-owned personal overrides
- `<workspace>/.agents/skills/`
  Bootstrap-managed repo/workspace generated skills
- `<workspace>/skills/`
  user-owned repo-local overrides

This gives us a clean override ladder:

- user repo override beats generated repo skill
- user personal override beats generated global skill
- generated skills stay in clearly owned locations

## Adapter Responsibilities

An eventual OpenClaw adapter should do four things only:

1. Merge canonical instructions
   Read `global/AGENTS.md` and `<repo>/AGENTS.md`, then produce the OpenClaw
   `AGENTS.md`.

2. Render OpenClaw workspace files
   Write `AGENTS.md`, `SOUL.md`, `TOOLS.md`, and optional `BOOTSTRAP.md` into
   the target workspace.

3. Sync curated skills
   Render or sync only curated canonical packages into the managed OpenClaw
   skill paths.

4. Preserve provenance
   Record which generated file or skill came from which managed package or
   adapter template.

## Auth Plan

Prefer OpenClaw onboarding paths that do not force long-lived raw secrets into
repo-managed config.

Recommended order:

1. Codex/OpenAI OAuth-style onboarding when supported in the target setup
2. env-ref or secret-ref onboarding for API keys when OAuth is not available
3. raw inline API key storage only as a last resort

This repo should not commit provider secrets, token caches, or OpenClaw auth
material.

## Import Policy For OpenClaw Skills

Do not bulk-import from:

- ClawHub
- `openclaw/skills`
- `awesome-openclaw-skills`

Instead, use this pipeline:

1. shortlist a candidate
2. inspect source code and install behavior
3. identify the actual capability we want
4. normalize it into a canonical managed package
5. record provenance in the catalog
6. render it through the OpenClaw adapter

This is the same anti-duplication rule we already use for Cursor-originated
content.

## Things To Skip For Now

- broad browser automation skills that duplicate existing browser capability
- reasoning or agent-orchestration packs that overlap with `superpowers`
- any skill that assumes ClawHub, Clawdbot, or hosted OpenClaw services as a
  hard requirement
- any marketplace skill that has not been source-reviewed
- anything in finance, crypto, or high-permission automation categories

## Suggested Implementation Phases

### Phase 1: Render-only adapter

- add an `openclaw` surface adapter in the Python engine
- render merged `AGENTS.md` plus generated `SOUL.md` and `TOOLS.md`
- do not sync skills yet
- keep everything reversible and file-based

### Phase 2: Managed skill sync

- define OpenClaw skill render targets
- sync curated canonical packages into managed skill paths
- add provenance tracking for generated skill payloads
- add doctor checks for collisions and duplicate capability ownership

### Phase 3: Workspace support

- allow `./install.sh workspace <path>` to also render an OpenClaw workspace
- support repo-local managed output paths
- preserve user-owned overrides in `<workspace>/skills/`

### Phase 4: Auth and onboarding helpers

- add a guided OpenClaw onboarding helper
- prefer OAuth or secret-reference-based setup
- validate that no secrets are written into tracked files

### Phase 5: Polishing

- add adapter status to the TUI
- add doctor checks for missing runtime files, broken skill paths, and stale
  generated workspaces
- add import review tooling for candidate OpenClaw skills

## Migration Notes From Earlier Mistakes

- do not mix detected presence with enabled state
- do not let local cache contents silently become managed packages
- do not use raw source plugin names as the long-term canonical identity if the
  capability should be merged
- do not let generated compatibility files become the only copy of durable
  instructions
- do not auto-commit, auto-push, or auto-install unreviewed external skills

## Decision Defaults

If we build the OpenClaw version next, start with these defaults:

- render-only adapter first
- no bulk import from `awesome-openclaw-skills`
- use `~/.openclaw/skills/` for bootstrap-managed global generated skills
- use `<workspace>/.agents/skills/` for bootstrap-managed repo generated skills
- preserve `USER.md` and `IDENTITY.md` as user-owned files
- treat `SOUL.md` and `TOOLS.md` as generated adapter-owned outputs
